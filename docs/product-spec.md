# ADP 제품 요구사항

> 치매 환자 보호자를 위한 감정 케어 및 기억 보존 서비스

## 1. 프로젝트 개요

치매 환자를 돌보는 보호자는 장기간의 돌봄 과정에서 피로, 슬픔, 무력감, 외로움 등의 감정을 경험하지만, 정작 보호자 자신을 위한 케어 서비스는 충분하지 않다.

기존 치매 관련 서비스는 배회 감지, 인지 훈련 등 환자 중심 기능에 집중되어 있다. 보호자가 자신의 감정과 돌봄 경험을 기록하고 가족과 공유하며, 환자에 대한 기억을 오래 보존할 수 있는 서비스는 부족하다.

ADP는 보호자가 자신의 감정을 객관적으로 돌아보고, 환자와 함께한 돌봄의 기록을 가족과 공유하며, 소중한 기억을 데이터로 보존할 수 있도록 돕는다.

## 2. 해결하려는 핵심 문제

- 환자 중심의 치매 돌봄 서비스는 많지만 보호자의 정서적 소진을 다루는 기능은 부족하다.
- 보호자의 돌봄 기록과 환자에 대한 기억은 시간이 지나면서 흐려지고 사라질 수 있다.
- 여러 가족 구성원이 함께 환자를 돌보는 경우 기록과 감정 상태를 가족 간에 공유하기 어렵다.

## 3. 기대 효과

- 보호자가 자신의 감정을 객관적으로 돌아볼 수 있다.
- 가족 구성원이 서로의 돌봄 상황과 감정 상태를 이해하고 부담을 나눌 수 있다.
- 단순한 일기장을 넘어 환자에 대한 기억을 장기적으로 보존하는 아카이빙 도구가 된다.

## 4. 핵심 기능

두 가지 핵심 기능은 하나의 화면인 **정원**에서 함께 제공된다.

### 4.1 감정 정원

보호자 본인의 감정을 텍스트로 기록하고, 기록된 내용을 분석해 감정에 맞는 꽃으로 시각화한다.

| 항목 | 내용 |
| --- | --- |
| 대상 | 보호자 본인 |
| 입력 | 보호자의 감정 및 돌봄 경험 텍스트 |
| 처리 | 텍스트 감정 분석 |
| 결과 | 감정에 맞는 꽃 생성 |
| 화면 표현 | 정원 주변에 꽃 배치, 감정별 색상으로 표현 |
| 목적 | 보호자의 감정 인식과 정서적 자기 돌봄 |

꽃의 종류와 색상은 감정 분석 결과에 따라 결정한다. 구체적인 감정 분류 체계와 색상 규칙은 별도 설계가 필요하다.

### 4.2 기억 나무

치매 환자에 대한 사진, 영상, 음성, 텍스트 등의 기억을 기록하고 하나의 나무에 시간 순서로 축적한다.

| 항목 | 내용 |
| --- | --- |
| 대상 | 치매 환자와 관련된 가족 구성원 |
| 입력 | 사진, 영상, 음성, 텍스트 등 환자에 대한 기억 |
| 처리 | 기억 기록 저장 및 시간순 정렬 |
| 결과 | 기억이 누적되는 나무 형태의 기록 |
| 화면 표현 | 정원 중앙의 고정된 나무, 기록이 나뭇잎처럼 축적 |
| 목적 | 환자에 대한 기억의 장기 보존과 가족 간 공유 |

## 5. 핵심 화면: 정원

정원 화면은 감정 정원과 기억 나무를 하나의 공간에서 보여주는 대표 화면이다.

- 화면 중앙에는 기억 나무가 고정되어 있다.
- 나무 주변에는 감정 기록에 따라 꽃이 배치된다.
- `FAB(+)` 버튼을 누르면 새로운 기록을 추가할 수 있다.
- 사용자는 추가할 기록의 종류를 선택해 감정 기록 또는 기억 기록 작성 화면으로 이동한다.
- 감정 정원은 보호자 본인의 감정 기록을 표현한다.
- 기억 나무는 환자에 대한 기록을 시간의 흐름에 따라 쌓아간다.

### 기록 추가 흐름

```text
정원 화면
  -> FAB(+) 선택
  -> 기록 종류 선택
      -> 감정 기록: 텍스트 입력 -> 감정 분석 -> 꽃 생성
      -> 기억 기록: 사진/영상/음성/텍스트 입력 -> 기억 저장 -> 나무에 누적
```

## 6. 대상 사용자

| 사용자 유형 | 설명 |
| --- | --- |
| 주 사용자(간병인/보호자) | 치매 환자를 직접 돌보는 가족 구성원. 소셜 로그인(카카오, 네이버, 구글) 또는 이메일 로그인을 사용할 수 있다. |
| 나무 멤버(가족 구성원) | 그룹화를 한 뒤 특정 환자의 기억 나무에 초대되어 기록을 열람하거나 작성할 수 있는 사용자이다. 친구 관계를 기반으로 한 그룹도 지원할 수 있다. |

## 7. 사용자 및 공유 모델

- 한 명의 보호자는 하나 이상의 기억 나무에 참여할 수 있다.
- 하나의 기억 나무에는 여러 가족 구성원이 멤버로 참여할 수 있다.
- 기억 기록은 해당 나무의 멤버에게 공유된다.
- 감정 기록은 기본적으로 작성자 본인의 개인 기록으로 취급한다.
- 향후 감정 기록을 가족에게 공유할지 여부는 기록별 공개 범위로 확장할 수 있다.
- 나무 멤버 초대와 기록 조회 권한은 그룹 단위로 관리한다.

## 8. 백엔드 초기 도메인 후보

제품 요구사항을 기준으로 다음 도메인부터 설계한다.

- `users`: 인증 사용자와 프로필
- `care_groups`: 환자 단위 또는 가족 단위 그룹
- `care_group_members`: 그룹별 사용자와 역할
- `emotion_entries`: 보호자의 감정 기록
- `emotion_analysis`: 감정 분류 및 꽃 표현 결과
- `memory_entries`: 환자에 대한 기억 기록
- `memory_assets`: 사진, 영상, 음성 파일 메타데이터
- `tree_events`: 기억 나무에 표시할 누적 이벤트

실제 테이블명과 필드는 Supabase 스키마 설계 단계에서 확정한다.

## 9. 권한 및 개인정보 원칙

- Supabase Auth를 사용자 인증의 기준으로 사용한다.
- 사용자는 본인의 감정 기록만 조회할 수 있어야 한다.
- 기억 기록은 해당 기억 나무의 멤버만 조회할 수 있어야 한다.
- 사진, 영상, 음성에는 민감한 개인정보가 포함될 수 있으므로 Storage 접근 정책을 별도로 설정한다.
- Supabase `service role key`는 FastAPI 서버에서만 사용하고 클라이언트 앱에 노출하지 않는다.
- 감정 분석 결과는 의료적 진단이 아니며, 서비스 내에서 진단 결과처럼 표현하지 않는다.

## 10. 확정된 DB 설계 결정

### 10.1 사용자 인증 및 식별자

- Supabase Auth를 인증 시스템으로 사용한다.
- `users.password`는 저장하지 않는다. 비밀번호가 필요한 경우에도 Supabase Auth가 관리한다.
- `users.id`는 Supabase Auth의 `auth.users.id`와 연결되는 `UUID`를 사용한다.
- 그 외 테이블의 기본 키와 외래 키는 기본적으로 `INTEGER`를 사용한다.
- 사용자와 연결되는 외래 키(`user_id`, 작성자·발신자·수신자)는 `users.id`가 UUID이므로 UUID 타입으로 정의한다.
- 서비스 프로필 정보는 `public.users`에 저장하고 인증 정보는 `auth.users`에서 관리한다.

### 10.2 기억 기록 조회 방식

- `memory_records`에는 `group_id`를 직접 추가하지 않는다.
- 그룹별 기억 기록은 다음 관계를 통해 조회한다.

```text
memory_records.patient_id -> patients.group_id
```

- 따라서 기억 기록 조회용 인덱스는 `group_id`가 아니라 다음 기준으로 둔다.

```text
(patient_id, record_date)
```

### 10.3 공통 데이터 처리

- `updated_at`은 PostgreSQL 트리거로 자동 갱신한다.
- `updated_at` 자동 갱신 대상 테이블에는 공통 `set_updated_at()` 트리거 함수를 적용한다.
- 그룹 멤버는 동일 그룹에 중복 가입할 수 없다.
- `group_members (user_id, group_id)`에 Unique 제약을 적용한다.
- 모든 시간 기록은 기본적으로 `timestamptz`를 사용한다.
- 날짜만 의미가 있는 값은 `date`를 사용한다.

### 10.4 그룹 정책

- 그룹에는 그룹장 개념이 없다.
- 모든 그룹 멤버는 동일한 권한과 역할을 가진다.
- 멤버 역할(`role`)과 가입 상태(`status`) 컬럼은 추가하지 않는다.
- 초대는 초대 코드를 입력하는 방식으로 처리한다.
- 사용자가 탈퇴하면 `group_members`에서 해당 멤버십을 삭제한다.
- 그룹 멤버는 동일한 권한으로 그룹 기록을 조회하고 작성할 수 있다.
- `groups.members`는 별도 집계값으로 관리하지 않고 `group_members`를 기준으로 인원 수를 계산한다.

### 10.5 개인별 환자 호칭

- `group_members.patients_nickname`을 유지한다.
- 그룹 가입 또는 환자 연결 시점에 애플리케이션이 `patients.patient_name`을 기본값으로 복사한다.
- 이후 사용자가 자신의 호칭을 개별적으로 수정할 수 있다.
- 이 값은 환자 원본 이름의 자동 동기화 값이 아니라 사용자별 호칭 스냅샷이다.

### 10.6 첨부파일

- `media.file_url` 컬럼명은 기존 설계대로 유지한다.
- 실제 저장 값은 공개 URL이 아닌 Supabase Storage의 `storage_path`를 기록한다.
- URL이 필요한 경우 API에서 Storage 경로를 기준으로 접근 URL을 생성한다.
- 별도의 `media` 연결 대상 제약은 현재 적용하지 않는다.

### 10.7 Row Level Security

- Supabase의 Row Level Security(RLS)를 적용한다.
- 그룹 멤버 여부를 기준으로 그룹, 환자, 기억 기록, 돌봄수첩 데이터의 접근을 제어한다.
- 감정 일기는 작성자 본인만 조회하고 수정할 수 있도록 한다.
- FastAPI에서 사용하는 `service_role_key`는 RLS를 우회하므로, API 계층에서도 현재 사용자의 UUID와 그룹 멤버십을 검증한다.

## 11. 보류 중인 결정

다음 항목은 현재 확정하지 않고 감정 일기 및 기능 상세 설계 단계에서 결정한다.

- 감정 일기에서 AI 추천과 사용자의 최종 감정 확정 방식
- 감정 일기 임시 저장 및 진행 상태
- `mood_status`와 행동 유형 등 돌봄수첩 선택지의 최종 목록
- `patient_daily_conditions`의 하루 기록 횟수
- 응원 기능의 횟수 제한과 문구 첨부 여부
- 기억 기록 반응 종류
- `anonymous_letters` 기능 포함 여부와 수신 정책
- 감정 통계 캐시 테이블 도입 여부
